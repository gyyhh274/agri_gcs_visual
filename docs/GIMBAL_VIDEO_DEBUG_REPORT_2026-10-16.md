## 4. 云台离线的发现与修复

### 4.1 单个 UDP 数据报包含多条 SDK 回复

机载日志观察到相机返回 45 字节、23 字节等数据报。原来的 `parseFrame()` 要求整个数据报长度恰好等于一条 SDK 帧，遇到合并回复会直接拒绝，导致明明收到数据却没有更新在线状态和姿态。

当前 `onReadyRead()` 改为在数据报中扫描 `55 66` 帧头，按载荷长度切出完整帧，逐条校验 CRC、解析内容；坏帧或无关字节之后继续寻找有效帧。只接受当前配置目标 IP 和端口的回复，断连后忽略迟到的数据。

这是有实机报文和回归测试支撑的具体缺陷；但没有证据证明它是此前所有“离线”现象的唯一原因。

### 4.2 绑定后立即断开 socket，破坏源端口保持

原流程是 `bind()` 后执行 `connectToHost()`，随后立即 `disconnectFromHost()`，但实际发送使用 `writeDatagram()`。这段连接/断开并不必要，还会关闭刚绑定的 socket，破坏“保持同一 UDP 源端口”的意图。

现在保留一次绑定的 IPv4 socket，直接使用 `writeDatagram()` 指定目标，并检查绑定是否成功。自动化测试确认同一对象重连前后的源端口相同。

### 4.3 重连时保留旧连接状态

原逻辑在重连时没有先复位 `connected`，而收到回复时仅在旧状态为离线时更新状态文本，可能出现已收到回复、界面仍停在“正在连接”的状态。

现在重连先清理状态、旧回复时间和已排队的数据；收到有效帧就更新在线文本。断连时清除目标地址，避免迟到回复重新置在线。

同时补充了转动状态下断连前立即发送零速度：先发送停止，再停定时器并清除地址。该行为通过本地模拟 UDP 服务测试，没有为这项测试实际转动硬件。

### 4.4 危险探针命令清理

移除了 `tools/siyi_probe.py` 最后一条 UDP `0x00` 心跳探测。项目已有说明指出 A8 mini 对这条 UDP 命令存在挂死风险；本次保留只读状态查询用途。

## 5. 视频实现与调试结果

### 5.1 原 macOS 后端限制

本机 Qt 5.15 的 Qt Multimedia 使用 AVFoundation，原先的 RTSP 和 `gst-pipeline:` 方式不能在该后端正常完成播放。仅修改 IP、缓冲或密码不足以解决这个后端兼容问题。

调试中曾使用过 GStreamer `appsink` 将视频转成 RGBA 再交给 Qt 绘制，能够出帧但仍有停顿。最终按用户要求切换到参考项目的硬解和 GL 显示实现，这个临时 appsink 方案没有保留在最终代码中。

### 5.2 当前保留的实现

复用了参考项目的 `A8VideoPipeline`，通过 `NativeVideoItem` 接入现有 QML 面板：

```text
rtspsrc（TCP、独立用户名/口令属性）
  → rtph265depay
  → h265parse
  → decodebin（优先 vtdec_hw）
  → videoconvert
  → glupload
  → glcolorconvert
  → qmlglsink
  → GstGLVideoItem / Qt Quick
```

实际运行日志确认解码器为 Apple VideoToolbox 的 `vtdec_hw`，输出 1920×1080。显示使用 GL 纹理，不再通过前述 RGBA appsink 绘制方案。

macOS 原生路径目前固定为 H.265/TCP，保留首帧等待、总线错误处理和重连机制。现有设置中的编码/传输选项不能理解为该原生路径已经支持 H.264 或 UDP。Linux 继续保留原有 Qt Multimedia/GStreamer 路径，本次没有在 Linux 或香橙派实机验证。

### 5.3 对比探针证据

为区分相机、中转和本机问题，执行过短时只读采样：

| 探针 | 观察结果 | 可以支持的结论 |
| --- | --- | --- |
| Jetson 直接读取相机，解包/解析后交给 `fakesink` | 30.04 秒收到 731 个编码帧；首帧约 0.055 秒；最大相邻到帧间隔约 0.081 秒 | 该采样区间相机编码输出连续 |
| Jetson 从本机 MediaMTX 读取，同样只解包/解析 | 30.04 秒收到 706 个编码帧；首帧约 1.053 秒；最大间隔约 0.081 秒 | 同期转发服务输出连续；不含 Wi-Fi 到 Mac 的路径 |
| Mac 原生 GStreamer 探针，编码与硬解输出分支 | 30 秒时编码分支 718 帧，`vtdec_hw` 分支 533 帧 | Mac 能收到连续编码数据且硬解工作，但两个计数不相等；不能据此直接断言硬解故障，尚未区分缓存、延迟和丢帧 |
| 地面站实际 GL 显示 | 出现约 24–25 帧/秒的连续片段，也出现多秒帧数不变 | 能显示真实画面；持续流畅性未解决 |

编码流探针不等于完整解码与显示测试；短时通过也不等于长期稳定。

早期一次直接拉流的 `gst-launch` 限时试验曾超时，后续上述并行采样又正常。因此，没有将早期超时作为“相机必然故障”的结论。

### 5.4 窗口后台状态与看门狗

观察到窗口置前后帧数推进改善；最小化或后台状态下，GL 显示计数容易长时间不推进，原先 5 秒无新帧就重连的策略造成反复拆建连接。

第一版只检查 `isExposed()`，仍观察到重连，说明这个条件不足。当前还检查 `isActive()`：窗口未暴露或未激活时刷新渲染看门狗计时，后台仍处理 RTSP 总线错误。

这项处理的作用是减少“后台停绘被当成断流”的误判。**它并没有保证后台画面持续更新，也没有证明前台所有停帧问题已解决。**另外，后台有过历史有效帧后，界面仍可能保持 `live`；这时需要看帧数是否推进，不能只凭绿色“图传实时”角标判断视频健康。

### 5.5 最后版本的实际证据

最后一次正常启动的会话，在报告采样时有 57 条每秒视频诊断记录：开始 5 条为 `connecting`，其后进入 `live`，最后帧数为 235，没有记录到 `retry`。

但日志中存在明显的连续停帧，例如 `frames=170` 和 `frames=215` 各保持多个采样周期不变。这说明“没有重连”只是看门狗行为变化，**不能当作卡顿已修复的证据**。本次也没有完成可重复的长时间前台/后台对照验收。

## 9. 当前使用方式与依赖

在本项目目录正常构建、启动：

```bash

```

`Start_GCS.command` 已具有可执行权限，也可从 Finder 双击。启动前应关闭旧地面站，避免多实例干扰诊断；当前没有增加单实例锁或自动终止其他实例的机制。

本机当前依赖参考项目的：

```text

MiniGUI_A8mini/.deps/GStreamer.framework/Versions/1.0
```

当前构建产物没有制作成可脱离参考项目目录的完整分发包。移动或删除参考项目依赖会影响运行；CMake 可通过 `AGRI_GCS_GSTREAMER_ROOT`、`AGRI_GCS_QMLGL_PLUGIN_PATH` 指定其他路径。硬件视频需要默认 OpenGL 模式，软件渲染路径没有验收 RTSP。

调试时还观察到：自动化框架在应用关闭后查询窗口，可能重新启动一个后台实例；这种实例的网络行为与正常终端启动不同。已清理该调试实例并通过启动脚本重新启动。尚未完成对这一启动差异的根因归因，不应简单断言为用户系统权限设置错误。

```bash

```

云台看 `[gimbal-diag]`，视频看 `[VS-diag] native frames=...`。视频判断应关注帧数持续推进，不能只看 `phase=live`。
